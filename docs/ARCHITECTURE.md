# Reprise architecture

## Data flow

Browser → validated Worker route → scenario generator → learned scenario prioritizer → two policy executions → ledger checks → optional counterexample reduction → run summary stored in D1 → replay/report returned to browser.

The source also provides an async local adapter for a user-owned agent. This adapter is separate from hosted JSON trace import.

## Event model

Virtual time is in seconds. Money is integer paise. Each scenario has one or two purchase intents, a per-purchase amount, recovery budget and a repeatable event schedule. Gateway state and the merchant-observed state are distinct. Supported events: checkout.failed, gateway.failed, gateway.captured, webhook.captured, recovery.request, consent.revoked, refund.request and telemetry.heartbeat.

The concurrency scenario represents two proposals based on the same stale budget snapshot. It is a logical race simulation, not a multithreaded database stress test. Recovery charges always succeed in the simulated gateway to make state violations observable. Scenario frequencies and amounts are designed test inputs, not measured merchant distributions.

## Invariants

1. Captured amount per purchase must not exceed the purchase value.
2. Recovery must have consent at execution time.
3. Recovery spend must not exceed its mandate budget.
4. Refunds must not exceed captured funds.
5. Clean recoveries must complete. A policy that holds every request fails this progress check.

The guarded policy reads current simulated authoritative state at execution, waits on unresolved originals, recognizes processed event IDs and rechecks consent, budget and refundable balance. Real systems also need transactional reservations, provider-specific idempotency and status reconciliation; this simulator does not claim distributed exactly-once delivery.

## Counterexample reduction

Greedily delete one event and rerun the same reference policy. Retain the deletion only if the original target invariant still fails. Repeat until no single deletion preserves it. Output is 1-minimal with respect to event deletion, not globally shortest or a formally proven root cause. Removing prerequisites can create an abstract trace that is useful for debugging but not a faithful standalone provider interaction.

## Learned prioritization

32-tree random forest, depth at most six. Features include one-hot scenario family, normalized delay/retry/consent timings, repeat count, budget ratio and timing differences. Labels are observed reference-policy test failures, generated by executing the simulator. 8,000 training cases and 2,000 disjoint held-out seeds. The model JSON contains tree arrays and measured model metadata. Server inference walks each tree.

The batch UI ranks a candidate pool four times its requested size, takes 80% from high-ranked candidates and fills 20% from remaining generated candidates. It is a fixed trained scheduler, not online active learning. Model failure probabilities are not calibrated for user-supplied agents. High test metrics reflect simple deterministic failure boundaries.

## API

- GET /api/workspace: recent D1 run summaries and model card. Storage errors are explicitly surfaced when relevant; metadata can still load.
- POST /api/workspace: validated seed, batch size 12–360 and strategy.
- POST with operation=inspect: reconstruct a seeded case and reduce its failure.
- POST with operation=trace: validate up to 200 normalized events and run both reference policies. Payload is bounded to 220 KB.

Mutating requests reject mismatched browser origins. Inputs use Zod; queries use prepared statements. No credentials, payment cards, external money endpoints or user PII are needed. The hosted app remains private. Public multi-tenant usage would require application-level identity, tenant scoping, quotas and per-user run ownership; the current single-owner table is not designed for that deployment.

## Persistence

D1 simulation_runs stores UUID, timestamp, seed, count, strategy and JSON summaries. Cases regenerate from seeds; no production transaction records are stored. Migrations are generated with Drizzle and applied at deployment. History replays use the current simulator code, so a future version must store simulator/model versions if cross-version exact regeneration is required.

## UI

React/Vinext, custom responsive CSS, Lucide icons and a Canvas event visualization. The canvas shows actual simulator events on event/agent/ledger lanes. The adjacent ledger and accessible event list provide the same state in text. Replay uses virtual time; motion respects reduced-motion preferences. Screens include test lab, history, model evidence and research. No decorative stock artwork or fake merchant metrics.

## Current validation and remaining gaps

Ten domain tests pass, including a 6,000-case invariant sweep and an all-hold liveness rejection. Production build succeeds. No browser visual QA, live Razorpay calls or independent LLM-agent benchmark has been performed. Refund lifecycle, partial captures, multiple currencies, fulfillment, actual provider fee economics, external database races and delivery guarantees are beyond v1.
